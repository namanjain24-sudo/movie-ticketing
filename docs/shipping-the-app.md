# Shipping the app to someone else's phone

Three things have to be true before an APK is worth sending anyone:

1. The API is on the internet, not on your laptop.
2. The build points at that API.
3. The APK exists and is somewhere they can download it.

This is the whole path, in order. Everything in the repo is already prepared
for it — what is left needs accounts, which is why it is yours to run.

---

## 1. The backend, on Render

`render.yaml` at the repo root describes the service and its Postgres, so
there is no console form-filling to get wrong.

1. Push `main` (the blueprint is read from the repo).
2. Render dashboard → **New → Blueprint** → pick `namanjain24-sudo/movie-ticketing`.
3. Render shows one web service (`boxoffice-api`) and one database
   (`boxoffice-db`). Apply.

First deploy takes a few minutes: it installs the workspace, generates the
Prisma client, bundles the API, runs migrations, and seeds the catalogue.

**Check it worked** — open `https://<your-service>.onrender.com/health/ready`.
Expected:

```json
{ "status": "ok", "database": "up" }
```

If it says `"database": "down"`, the service and the database ended up in
different regions. Both are pinned to `singapore` in the blueprint; if Render
refuses that region on the free plan, change **both** to `oregon` and redeploy.

### What the blueprint already handles

- **Secrets.** `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` and
  `PAYMENT_WEBHOOK_SECRET` are generated by Render. Nothing secret is in git.
- **The UTC pin.** Prisma maps `DateTime` to `timestamp without time zone`, so
  a non-UTC connection shifts every value and breaks hold expiry in a way that
  looks like a locking bug. `src/lib/database-url.ts` appends the option to
  whatever URL the host hands over.
- **Seeding, once.** `prisma/seed.ts` is destructive — it clears bookings
  before rebuilding the catalogue. The start command runs
  `db:seed:if-empty`, which only acts on a database with no films, so a
  restart can never delete a ticket someone booked.
- **No random payment failures.** The mock gateway declines one payment in ten
  by default, which is right for the test suite and wrong for a demo.
  `MOCK_PAYMENT_FAILURE_RATE` is `0`.
- **Redis is absent on purpose.** It only carries realtime seat fanout, and
  every call site tolerates it being gone. Booking is unaffected; seat changes
  arrive on the next refetch rather than being pushed.

### The free plan's one real catch

A free service sleeps after 15 minutes idle and takes roughly a minute to wake.
The app handles this rather than showing a scary error: it pings `/health/live`
at launch so the server wakes while the intro is on screen, and a `GET` that
times out is retried once on a 50-second budget. Mutations are never
auto-retried — the user taps again, and the idempotency key makes that safe.

Still, the first open after a quiet spell is slow. If you are demoing live,
open the app yourself a minute beforehand. A free uptime pinger
(cron-job.org hitting `/health/live` every 10 minutes) removes it entirely.

## 2. Point the build at it

`apps/mobile/eas.json` assumes the service is called `boxoffice-api`:

```json
"EXPO_PUBLIC_API_URL": "https://boxoffice-api.onrender.com"
```

Render appends a suffix if that name is taken. **Check the real URL in the
Render dashboard and put it in both `preview` and `production`.** Getting this
wrong is the single most likely reason a finished APK shows "cannot reach the
server" on every screen.

---

## 3. Build the APK

```bash
npm install -g eas-cli
eas login                        # your Expo account
cd apps/mobile
eas init                         # once: writes extra.eas.projectId into app.json
eas build --profile preview --platform android
```

`preview` is the profile that produces an installable `.apk` (the production
profile builds an `.aab`, which is for the Play Store and cannot be
side-loaded). The build runs on Expo's machines; when it finishes you get a
download link.

Commit the `app.json` change `eas init` makes — the project id belongs in git.

---

## 4. Get it to people

Two options, both already wired up:

- **The link EAS gives you.** Fastest. Send it; Android warns about installing
  outside the Play Store, they tap through it.
- **A GitHub Release.** The landing page's every Download button already points
  at `/releases/latest`. Create a release on
  `namanjain24-sudo/movie-ticketing`, attach the `.apk`, and the site starts
  serving it with no further changes.

Tell whoever installs it: **Settings → allow install from this source** is
expected for any APK that did not come from the Play Store.

### The demo login

The seed creates `demo@example.com` / `DemoPassw0rd`. They can also register
their own account — it is a real signup against a real database.

## Still outstanding

**Google Maps on the cinemas tab.** `app.json` references
`$GOOGLE_MAPS_ANDROID_KEY`. Expo Go uses Expo's own key, so the map works in
development and will be blank in your APK until you add one:

1. Google Cloud Console → enable **Maps SDK for Android**.
2. Create an Android API key, restricted to package `com.naman.mobileapp`.
3. `eas secret:create --name GOOGLE_MAPS_ANDROID_KEY --value <key>`, then rebuild.

Everything else — the cinema list, distances, directions handoff, booking, seat
map, tickets — works without it. Only the embedded map is affected.

**The free Postgres expires after 90 days.** Render will email you. Exporting
and restoring to a fresh instance takes a few minutes; nothing in the app
needs changing.
